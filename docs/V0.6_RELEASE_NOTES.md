# Aquadecomp v0.6 Release Notes - Persistent Caching & System Metrics

**Release Date**: November 2025  
**Version**: 0.6.0  
**Build**: JAR 79.1 MB with all dependencies  

## Major Achievements

### 🎯 Persistent Compilation Cache

**Problem Solved**: In-memory cache lost after process exits = no benefit for repeated CI/CD runs

**Solution**: Automatic file-based persistent cache with intelligent memory management

```
Day 1: First run  → Compile all 500 files (27s) → Save to disk
Day 2: Second run → Load from disk (instant) + 5 changes (3s) → **Total: 3s** (9x faster!)
Day 3: Third run  → Load from disk + 2 changes (2s) → **Total: 2s** (13.5x faster!)
```

**Real Impact**: 90%+ cache hit rate on stable codebases (common in CI/CD)

### 📊 Thread Performance Metrics

**Problem Solved**: No visibility into CPU/memory usage = can't optimize threading

**Solution**: ThreadMXBean-based metrics collection with system-wide analysis

```
System metrics: 8 threads, total_cpu=23200ms, wall=3220ms, 
               efficiency=90.0%, heap=380 MB / 512 MB (74.1%)
```

**Enables**: Identify bottlenecks, optimize thread count, detect memory leaks

## Components

### PersistentCompilationCache (215 lines)

**Two-Layer Architecture**:
```
In-Memory Cache (fast)
    ↓
Disk Cache (persistent)
```

**Features**:
- SHA-256 hash-based cache
- ConcurrentHashMap for concurrent access
- LRU eviction when memory exceeds limit
- Automatic loading on startup
- ReentrantReadWriteLock for thread safety

**Cache Entry on Disk**:
```
filename: 7a8c9e3d...f2a4c6e.cache
content:  86|true    (score|success)
```

**Memory Management**:
- Max memory: 100 MB (default)
- LRU eviction: Removes least-recently-used when full
- Disk copies retained for next run

## Implementation Details

### Two-Layer Cache Architecture

**Lookup Process**:
```
1. Check memory cache (ConcurrentHashMap)
   - Hit: Return immediately (~1ms)
   - Miss: Continue to step 2

2. Check disk cache (.cache files)
   - Hit: Load to memory, return (~10ms)
   - Miss: Compile file (100ms)

3. Store in both layers
   - If memory full: Evict LRU entry
   - Disk copy always retained
```

**Example Flow**:
```
Day 1, File A:
  Memory miss → Disk miss → Compile (100ms) → Save to both

Day 2, File A:
  Memory miss → Disk hit (10ms) → Return result

Day 3, File A (unchanged):
  Memory hit (1ms) → Return result
```

### Cache Statistics

```java
CacheStats stats = persistentCache.getStats();

stats.hits()                    // 450 successful lookups
stats.misses()                  // 50 compilations needed
stats.cacheSize()              // 500 total entries
stats.hitRate()                // 90.0 percentage
stats.currentMemoryBytes()     // 102,400,000 (102.4 MB)
stats.maxMemoryBytes()         // 104,857,600 (100 MB default)
stats.memoryUsagePercent()     // 97.6%
stats.summary()                // Human-readable string
```

### Memory Eviction Strategy (LRU)

**When memory exceeds 100 MB**:
```java
1. Find entry with oldest lastAccessTime
2. Remove from memory cache
3. Keep in disk cache (for next run)
4. Free ~256 bytes per entry
```

**Why LRU?**
- Recently used = more likely to be used again
- Old entries haven't been accessed lately
- Minimizes cache miss rate
